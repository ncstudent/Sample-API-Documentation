Catalog API / Guides

Data layer: Node.js + MongoDB

CECompany Employee  Version 1.03

The Catalog API stores intellectual property records and training materials as MongoDB documents. This guide covers the document structure, route behavior, and local testing workflow.

Minimum RequirementsNode.js 18 with MongoDB 7.0 reachable at MONGO_URI (default mongodb://localhost:27017).

Document structure

FieldTypeDescription
catalogIdstringIndexed Unique identifier (e.g. CAT-0042).
titlestringDisplay name of the item.
typestringip or training.
ownerstringTeam or person responsible for the item.
descriptionstringOptional summary.
tagsarray of stringsOptional search labels.
createdAtDateSet by the server on insert.
updatedAtDateSet by the server on every update.

Connect

db.js
const { MongoClient } = require('mongodb');

const client = new MongoClient(process.env.MONGO_URI || 'mongodb://localhost:27017');
let items;

async function connect() {
  await client.connect();
  items = client.db('Catalog').collection('items');
  await items.createIndex({ catalogId: 1 }, { unique: true });
  return items;
}

module.exports = { connect, collection: () => items };
Create only one ConnectionCall connect() at startup. The driver manages a connection pool, so as not to create a new client per request.

Create an item

async function createItem({ title, type, owner, description = '', tags = [] }) {
  const now = new Date();
  const catalogId = 'CAT-' + String(await items.countDocuments() + 1).padStart(4, '0');
  const doc = { catalogId, title, type, owner, description, tags, createdAt: now, updatedAt: now };
  await items.insertOne(doc);
  return doc;
}

If catalogId collides with an existing document, MongoDB throws error code 11000 and the route returns 409.

List items

async function listItems({ type, page = 1, limit = 20 }) {
  const filter = type ? { type } : {};
  const [results, total] = await Promise.all([
    items.find(filter).sort({ createdAt: -1 })
      .skip((page - 1) * limit).limit(limit).toArray(),
    items.countDocuments(filter),
  ]);
  return { results, page, limit, total };
}

Replace an item

async function replaceItem(catalogId, { title, type, owner, description = '', tags = [] }) {
  return items.findOneAndReplace(
    { catalogId },
    { catalogId, title, type, owner, description, tags, updatedAt: new Date() },
    { returnDocument: 'after' }
  ); // null when no document matches; the route returns 404
}

Delete an item

async function deleteItem(catalogId) {
  const { deletedCount } = await items.deleteOne({ catalogId });
  return deletedCount === 1;
}

Routing & Local Testing

CECompany Employee  Version 1.03

All routes are served under /api/v1 require a bearer token and return JSON.

Endpoints

MethodPathPurpose
POST/itemsCreates a Catalog item and assigns a unique catalogId.
GET/itemsReturns items with optional type filtering and page-based pagination.
GET/items/:catalogIdReturns a single item identified by catalogId, or 404 when none exists.
PUT/items/:catalogIdReplaces an existing item; the required fields must be supplied because the document is replaced rather than merged.
DELETE/items/:catalogIdDeletes the matching item and reports whether a document was removed.
POST detailsSee Intellectual Property & Learning Materials for POST fields.

Call the API from Postman

  1. Import Catalog.postman_collection.json from the /docs folder.
  2. Create an environment with baseUrl set to http://localhost:3000/api/v1 and token set to dev-token.
  3. In the collection settings, set Authorization to Bearer Token with the value {{token}}.
Accessing for the first timeBe sure to run the AuthInit.sh for default key & token data. Otherwise you must manually Post the Bearer token credentials.

Adding a New Field

TWTechnical Writer   Updated 09.22

Sometimes old documents come alive. An identity might split into two, new information might emerge, or a record’s circumstances might simply change. This tutorial will walk you through how to add a new field to the Catalog API so your records can keep up with those changes.

Let’s start with a simple one: a document's status. Take caution. Even a single "simple" field propogates changes everywhere - from MongoDB documents, request validators, create and replace operators, to this very documentation.

1. Define the allowed values

The API accepts three statuses: draft, active, and archived. Keep the allowed values in one place so the route and data layer use the same definition.

const allowedStatuses = ['draft', 'active', 'archived'];

2. Update the create operation

Add status to the function parameters and store it on the document. New items default to draft when the caller does not supply a value. 

async function createItem({
  title,
  type,
  owner,
  description = '',
  tags = [],
  status = 'draft'
}) {
  const now = new Date();
  const catalogId = 'CAT-' + String(await items.countDocuments() + 1).padStart(4, '0');
  const doc = {
    catalogId, title, type, owner, description, tags, status,
    createdAt: now,
    updatedAt: now
  };
  await items.insertOne(doc);
  return doc;
}

3. Validate requests

The router should reject an unknown status before the request reaches the database. When the field is omitted, use draft as the default.

routes/items.js
const { title, type, owner, status = 'draft' } = req.body;

if (!title || !owner || !['ip', 'training'].includes(type) ||
    !allowedStatuses.includes(status)) {
  return res.status(400).json({ error: 'invalid_parameters' });
}
Why validate here?Rejecting an invalid value at the API boundary gives callers a predictable 400 response and prevents invalid documents from reaching the database.

4. Update replacements

Because PUT /items/:catalogId replaces the document, it must include status in the replacement object. Otherwise an existing status would be dropped.

async function replaceItem(catalogId, {
  title,
  type,
  owner,
  description = '',
  tags = [],
  status = 'draft'
}) {
  return items.findOneAndReplace(
    { catalogId },
    { catalogId, title, type, owner, description, tags, status,
      updatedAt: new Date() },
    { returnDocument: 'after' }
  );
}

5. Test the new behavior

Test both the default and the validation rule. The first request should store draft; the second should return 400.

it('defaults a new item to draft', async () => {
  const response = await request(app)
    .post('/api/v1/items')
    .send({ title: 'Example', type: 'training', owner: 'L&D' });

  expect(response.status).toBe(201);
  expect(response.body.status).toBe('draft');
});

it('rejects an invalid status', async () => {
  const response = await request(app)
    .post('/api/v1/items')
    .send({
      title: 'Example',
      type: 'training',
      owner: 'L&D',
      status: 'pending'
    });

  expect(response.status).toBe(400);
});

6. Update the API reference

Add status to the request table and document the accepted values and default.

ParameterTypeRequiredDescription
statusstringNoEither draft, active, or archived. Defaults to draft.

End Result

All newly created items now have an explicit lifecycle:

{
  "catalogId": "CAT-0042",
  "title": "Onboarding Workshop Slides",
  "type": "training",
  "owner": "Learning and Development",
  "status": "draft"
}

And that’s all there is to it. With status now carried through the API, clients can rely on the same information wherever - and whenever - the record is read or updated.
